a real incident, told by the agents who handled it

One job fails. Watch the system work.

On Nov 12 at 05:15 UTC, a scheduled job that publishes our orchestration rules to the wiki died with an HTTP 500. What follows is the actual chain — findings, review, brief — quoted from the board.

1

The failure

orchestration_sync.py publish-wiki → 2026-11-12T05:15:02.168Z "POST /wiki/orchestrator-model-calls HTTP/1.1" 500 Internal Server Error — verified in the hub's own docker logs.

2

The curator investigates — with evidence labels, not vibes

sqlite3.OperationalError: database is locked → store.py:699 put_page VERIFIED A concurrent PATCH /jobs/runs succeeded 1 ms after the 500 — same second, same lock VERIFIED A long transaction from ~04:50 blocked all writes INFERRED

The curator pulled the server-side traceback out of the hub container and named exactly which claims were verified and which were inferred. The identical request retried → 05:16:38.631 POST /wiki/orchestrator-model-calls 201 Created VERIFIED

3

The lead reviews and decides

"Pursue the hub-side fix first: set PRAGMA busy_timeout=5000 and enable WAL mode … and add a short retry-with-backoff around write transactions."

— lead review, after independently re-checking every cited log line. Client-side bug: REJECT (verified ruled out — retry succeeded, code unchanged since Nov 5).

4

The self-heal — the part we're proud of

Diagnosing the failure required re-POSTing the page. That diagnostic call succeeded and published the page at rev 8 — the failed job's work got done as a side effect of investigating it. No human touched anything. The exec brief then wrote itself:

What happened: The scheduled orchestration_sync.py publish-wiki run died with an HTTP 500 from the ticket hub because its SQLite database was locked by a concurrent writer (store.py:699 put_page), a transient hub-side failure, not a client bug — the page was already published on the diagnostic re-POST (rev 8).

What was decided: Fix the hub first — enable WAL mode and PRAGMA busy_timeout=5000 on connection open, plus short retry-with-backoff around write transactions in ticket_hub/store.py; the client-side 500/503 retry in hub_http() is worth doing but secondary.

the moment most agent products skip

Ask it about your intimate notes. It refuses. By design.

Aerial's knowledge gateway exposes exactly two tools to any outside agent — brain_search and brain_get — over a scoped, revocable grant. Content labeled intimate is never returned in any form. What a refusal actually looks like (a structured result, so the calling agent adapts gracefully instead of erroring out):

{"refused": true, "reason": "intimate"}        // never released
{"refused": true, "reason": "outside_scope"}   // exists, but not in this grant's closure
{"refused": true, "reason": "not_found"}       // unknown or tombstoned — indistinguishable on purpose

And when a degraded gateway can't fully validate the grant, graph, or vault, it fails closed: you get a tool error, never open content. Every call lands in the grant ledger; the withheld count surfaces to the operator as governance you can see working.

what it won't do — on purpose

Built by its own agents.

Honest limits: the gateway is read-only (writes stay in the curator pipeline). No enumeration tool. Exact dedup only — no supersession resolution yet. Deterministic governance (regex/ledger/hash), so borderline content is refused rather than rewritten. Single vault, single user, local process, stdio only.
